# 把问题讲清楚，把文档写到能用

写回复或解释时看前两节。写技术材料时按第三节选择文档类型，按第四节区分评审者、维护者和最终用户。邮件、公告和简报见第五节。案例中的界面、记录与接口约定均为示例材料。

## 一、回答、进度、纠错

动笔前先把读者的问题缩成一句可以回答的话。读者问“还要再交一次吗”，开头就应当能看出还要做什么。读者问“为什么会这样”，先说已经查到的原因。只有现象可以确认时就先说现象，再说哪项证据能区分原因。

| 手里有什么 | 写的时候做什么 | 发出前核对 |
|---|---|---|
| 答案明确 | 先给判断，再补一个真正改变做法的条件。能用一句话答完就停。 | 删去开头一段后，真正的答案是否才刚出现？如果是，把答案提前。 |
| 结论取决于条件 | 写出条件及其后果。几种情况都能简短说明，就直接给出分支。缺少关键输入且选错会影响决定时，只问能区分分支的问题。 | 读者能从自己看到的状态选出下一步吗？ |
| 有新进展 | 把已经完成的动作和已经验证的结果分开。说明这次进展怎样影响交付。材料给了负责人或日期才写。 | “已修复”“已发布”“已通过”各自对应哪项记录？ |
| 遇到故障 | 先交代受影响的对象、可观察的现象，再写已证实的原因、可行的下一步。两种原因尚难区分时，写哪项检查可以区分。 | 一次测试超时，最多能说明这次测试没有返回结果。 |
| 收到纠正或异议 | 更正错误的判断，重看依赖这一判断的数字、标题、结论和文件。给出修正结果。对方要求解释时，补上原判断错在哪里。 | 旧说法是否还留在表格、图注、代码注释或摘要里？ |
| 对方失望或着急 | 承认对方具体遭遇的影响，再回答当前能做的事。自己造成错误时说清过失与补救。 | 道歉、安慰或称赞是否代替了实质答复？ |

**对方问还要多久。** 数一遍剩下的耗时步骤，找出最可能影响完成时间的那一步。只有拿到本次运行或可比任务的耗时记录，才给估算范围。比如还剩两批，最近每批用时 3–4 分钟，可以答“如果两批都一次通过，约需 6–8 分钟”。目前只知道还剩两批时，就报两批。任务重试或外部排队时间未知，就把影响估算的那一点说清。

### 如何判断一个限定该不该留

逐句问自己“删掉后，读者会做错什么，或会把哪个结论理解得过强？”答得出来，就把限定改成具体对象、触发条件或观测范围，放在受影响的那句话旁。两处限定指向同一件事时，保留最接近关键决定的一处。答不出实际影响，且这句话只是在替一个无人提出的反对意见答辩，就删掉。真实的负面结果照写。谁会受到影响、是否需要停止操作等关键信息，即使增加篇幅也保留。

**中文短答。** 已知报名页显示“已提交”，只有收到“退回补材料”通知才须再次提交。问题是“我明天还要再交一遍吗？”

- 原稿写道“为避免产生误解，需要说明的是，通常并不能简单地认为所有用户都需要再次进行相关操作。”
- 可以改为“不用。页面已经显示‘已提交’。如果后来收到‘退回补材料’通知，补齐后再提交一次。”
- 原稿中的“通常”改成了读者能看见的条件，结论只涉及提交状态。录取结果和审核时限均超出材料能说明的范围。

**English status update.** A test log records a passing CSV export and a timeout during the PDF test.

- The draft reads “We are pleased to report meaningful progress on export validation, although it is worth noting that the situation with PDF may require further attention.”
- Send “CSV export passed. The PDF test timed out, so we still need to verify PDF export.”
- The timeout belongs to the test. Calling PDF export broken would require evidence about the product. If someone is deciding whether to release a PDF feature, put the unverified PDF result first.

## 二、给没有项目背景的人解释

1. **找到卡点。** 对方可能认得每个词，仍不知道两件事之间有什么联系。分清这次要解释的是名词、机制、差异、操作还是某个决定。已知读者熟悉的起点可以直接使用。
2. **补上中间的一步。** 按先后追踪一次操作。谁发出什么？谁收到后做了什么？状态保存在哪里，又怎样影响下一步？只写解释结果所需的环节。每个代词都应能找到对象，每个“因此”都应能从前文推出。
3. **把术语接回场景。** 首次出现的内部简称、代码名和借词，换成读者认得的名称，或给一个具体动作。读者随后还要在界面、表单或文献中找这个术语时，保留原名。对专家先讲变化、假设或新发现，省去双方已知的定义。
4. **走完一个例子。** 用同一对象把输入、过程、结果讲完。类比可以解释陌生关系。若类比暗示了错误的保证，直接改用真实机制。新加的教学例子应能与项目事实区分。
5. **从读者的任务验收。** 写操作就从文中实际找出第一步和成功标志。写机制就试着根据前文预测一个条件变化后的结果。读者要求互动学习时，可以让对方试解释一次。普通答复在说明完成后收住。

**例。** 新同事看到“草稿只保存在本机”，问为什么换一台电脑看不到。材料已说明填写时浏览器保存草稿，点击“提交”后服务器才保存。

- 原稿写道“该现象由客户端持久化策略和服务端同步边界共同决定。”
- 可以改为“填写时，浏览器把草稿存到你正在用的电脑上。点‘提交’后，服务器才会收到表单。因此换电脑时，另一台电脑读不到原来的草稿。”
- 检查读者能否预测“关掉第二台电脑，再回原电脑找草稿”与“在第二台电脑查看已提交的表单”为什么涉及不同位置。材料没有说明草稿保留多久或谁能查看已提交表单，这些结论需要另查。

**从系统字段改写成读者能用的通知。** 第一遍先把字段和值还原成事实。假设记录为 `delivery_status=held`、`reason=address_missing`，可确定地址缺失导致包裹暂缓配送。第二遍关掉字段表，问收件人究竟需要知道什么。可写“包裹暂未配送，还缺收件地址。”只有确认订单页可以补填地址，才加“请在订单页补全收件地址”。给维护 API 的人则保留字段名，便于对照日志。

## 三、操作、接口与故障说明

先定文档用途，再决定结构。一份长 README 可以分别链接给第一次使用的人和查接口的人，避免让读者从背景介绍里翻找命令。

| 读者要完成的事 | 写作顺序 | 最有用的检查 |
|---|---|---|
| 第一次跑通 | 前提、最小操作、看得见的成功结果，再给下一步入口 | 从空白起点读一遍，检查账号、输入、起始目录或环境有没有跳步 |
| 完成某项操作 | 把影响操作的条件放在对应步骤之前。操作后给预期结果。按实际失败情形补分支 | 界面按钮、字段、命令行参数、引号和参数顺序是否与材料一致 |
| 查某个参数或 API | 列出对象、类型、单位、适用范围、返回值和真实的错误行为，按需要补例子 | 分清缺省、空值和零，核对包含或排除端点、时区、排序和副作用 |
| 理解设计取舍 | 从要解决的问题开始，讲清机制、选择理由和材料已知的代价 | 读者能从说明里判断何时适用、哪个条件变了需要重新考虑吗？ |
| 恢复失败的操作 | 保留原始错误或状态码，解释其含义，按可观察的条件给出排查顺序和成功标志 | 可重试的依据是什么？重复提交可能产生重复记录时，要先查状态 |

**操作说明的改法。** 已知测试环境页面使用英文标签，用户在 `Settings` 的 `Alerts` 中打开 `Email alerts`，点击 `Save` 后显示 `Saved`。

- The draft reads “Users can leverage the configuration functionality to facilitate notification enablement.”
- Write “Open **Settings → Alerts**. Turn on **Email alerts** and select **Save**. Wait for the **Saved** message.”
- 中文版可以直接对照界面写成“打开 **Settings → Alerts**，开启 **Email alerts**，再点 **Save**。出现 **Saved** 表示设置已保存。”页面信息只证明保存成功。是否实际收到邮件还需要投递记录或测试邮件。
- 报错若为 `403` 且接口文档明示仅管理员可修改该设置，就在对应步骤旁说明管理权限。若只拿到 `403`，可说“服务器拒绝了这次请求”，核对权限配置后再写具体原因。

**如何把接口约定写成可查的参考。** 假设接口定义为 `read_batch(offset=0, limit=50)`。已知 `offset` 是从零起算的记录序号，`limit` 是单次最多返回的条数，仅接受 1 到 200 的整数。从指定位置开始已没有记录时返回空列表，`limit=0` 会抛出 `ValueError`。原稿“分页参数灵活，可根据业务需求设置”无法指导调用者。可改为下面这段。

> `read_batch()` 从第 0 条记录开始，最多返回 50 条。用 `offset` 指定起始记录的序号，用 `limit` 指定最多读取几条（1–200，含两端）。例如 `read_batch(offset=50, limit=20)` 最多读取 20 条，从序号 50 开始。若起始位置已经没有记录，返回 `[]`。传入 `limit=0` 会抛出 `ValueError`。

逐个试读示例中的边界。空列表是正常的结束信号，异常涉及参数错误，两者需要不同的调用逻辑。接口若允许并发写入，读取两批之间的排序或一致性得查接口约定后才能说明。

命令、代码样例、配置键、路径、错误字串与翻译后的正文分开排。一步包含会覆盖文件、发出通知或产生收费的动作时，先写材料已知的具体后果。可以验证时核对界面、实现或测试输出。只审阅了源码就按源码说明行为，报告执行结果需要运行记录。

## 四、写给维护者、评审者和用户

**改注释前，先问“以后改哪一行会踩坑”。** 找到相关实现、调用处、测试或对象约定，从中辨认顺序、单位、边界、外部兼容性或重试语义。行内注释放在容易改错的位置。公共函数的调用约定写进文档字符串，例如输入单位、空输入的结果、抛出的异常和调用方承担的条件。只选实际影响调用者的项。接口字段名和异常类名按代码原样书写。

例如，已知传输层要求以秒传入超时时间，项目配置用毫秒。对 `seconds = timeout_ms / 1000` 写“除以 1000”只是在复述代码。可以写“配置以毫秒计，传输层的超时参数以秒计。”英文可写 “The transport expects seconds. Configuration values use milliseconds.” 若同一信息已经清楚写在类型或函数约定里，可直接保留代码。

**同一事实，改成三种成品。** 假设服务在处理一条消息后才提交消费位置。处理器抛错时位置没有提交，服务重启后会重送该条消息。本次测试覆盖处理成功与抛错两条路径。“提交消费位置”让系统记住下次应从哪条消息开始读取。

| 放在哪里 | 可以直接用的文字 |
|---|---|
| 维护注释，紧靠提交位置的调用 | `# 处理器抛错时须保留原位置，服务重启后才能重送这条消息。` |
| PR 描述，给负责核对变更的人 | “将位置提交移到消息处理完成后。已测试处理成功时提交，以及处理器抛错时保留原位置。请重点看抛错路径上的提交顺序。” |
| 发布说明，给使用消息服务的人 | “如果处理一条消息时出错，下次启动服务时会重新投递这条消息。” |

三处都保留了触发条件。这个机制允许重送，无法据此承诺注册的处理器只会执行一次。如果材料只给出代码差异，应先检查调用路径，再决定是否能写用户可见结果。改注释类任务通常只改注释，逐行确认代码、参数、缩进和返回行为与任务要求一致。

## 五、邮件、公告、简报与口播

- **邮件或工作消息。** 先找收件人此刻需要做的决定。把所需动作与材料给出的截止时间放在前面，再补与决定有关的理由和附件。对方不需要回应时，报告实际结果就够了。正式程度按双方关系调整。
- **公告、表单和界面文案。** 写清适用人群、可以做什么、哪些是必须项、何时生效。按钮写动作，辅助文字写条件。把法定或正式措辞照原样保留，需要时在旁边另做通俗解释。未提供负责机构、例外条款或截止时间时不要补造。
- **业务简报、幻灯片和口播。** 标题能表达有依据的发现时直接写发现。图旁写比较基准、单位、期间和口径。读者要做决定时，解释这一发现怎样影响选择。讲者备注按能顺口念出的句子写，听众看不到的表格位置改成具体对象。
- **产品说明或公开文章。** 把“能力升级”“体验提升”等评价还原成谁能做什么。已知变更若是财务人员现在能看到本部门报表，成稿可写“财务人员现在可以查看本部门的报表。”原材料若仅说明团队正在调整报表权限，就写进行中的工作。样本内的数字要带分母或比较基准。
- **给不同行业、地区或语言的读者。** 沿用正式名称和对方会看到的界面文字。繁体地区按任务选用台湾或香港的惯用词。转写英文用当地常见的搭配与称呼。一份中英并排的公告要逐项对齐动作、义务、受众和时限。

**单独读一遍链接文字。** 把公告或表单里的链接抽出来。三个链接若都叫“点这里”，读者很难判断该选哪一个。可以依实际目的页分别写“下载申请表”“查看材料清单”“查询申请进度”。复查每个目标，网页链接名可改得清楚，步骤中引用的真实按钮名须与界面一致。

**邮件例。** 已知评审会在周四，负责人请参会者在周三 17:00 前从附件 A、B 中选一个排期，材料使用团队本地时间。

- 原稿写道“为了更好地做好后续相关协同工作，烦请大家后续对有关方案积极反馈。”
- 可直接发送“请在周三 17:00 前回复你倾向的排期，两个选项在附件 A 和 B。周四评审会将讨论排期。”
- In English, write “Please reply by 5 p.m. Wednesday with your preferred schedule from attachment A or B. We’ll discuss the schedule at Thursday’s review.”
- 跨时区发送时写清已确认的时区。只有会议安排而没有决定权时，用“讨论”准确传达会议作用。

## 交付前，从成品上验收

选与当前任务有关的检查。短答检查读者能否直接找到结论。给外行的解释检查连接两步的机制是否写出来。操作文档从所写前提走到成功标志。代码文字对回实际行为，特别检查与前一版不同的边界。面向团队之外的文稿，单独阅读成品，去掉依赖这次聊天才能懂的“按上条要求”“做了如下优化”等句子。遇到无法核实且会改变读者行动的信息，写清那个缺口。核验过程留给需要了解它的读者。
