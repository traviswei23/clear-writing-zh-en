# 一句话该怎么处理

先看用户指定的事实、用途、编辑权限和体例，再选下面的做法。每项给出一个当场可做的判断。来源对照通过链接指到对应判断。

<a id="answer"></a>

## 直接作答

先写读者要知道的事实、判断或行动。在草稿里暂时遮住第一段。如果后文才回答问题，把那个答案移上来。对“能否导出 CSV”先答能否，再给入口或所缺条件。故事、悬疑和按时间复盘保留读者需要的展开方式。

<a id="status"></a>

## 进展与纠错

把“已做”“已验证”“尚待确认”分别对回具体对象。验证了网页版登录，就报这个范围。结论更新时，重读依赖旧结论的正文、图注和操作步骤，实际修正它们。道歉或致意只有在回应具体影响时才有意义，一句就够。

<a id="scope"></a>

## 编辑权限

根据‘只指出问题／校对／润色／重写’划定可动的范围。审校意见指出原句位置、可能的误读、改法和保留项。用户要轻改时，一句话足以澄清就保留其他段落。已给出修改指令可以直接改，用户要先看提案时才等待选择。

<a id="voice"></a>

## 作者声音

从同一作者、相近受众的样本提取两三个可观察习惯，例如称呼、句子怎么转折、是否直接提出要求。把习惯用于新稿。第一人称只承担作者真实的判断或行动。保留原本有意的犹豫、幽默、克制或锋芒。缺少样本就沿用原稿。

<a id="limit"></a>

## 限定与防御

遮住限定句，比较读者能推出什么。删掉后适用范围、风险、确定程度或承诺改变，就留下，并把条件与影响放在同一句或相邻句。只有‘可能也许大概’时，找出哪一步确实未知。已经回答过的假想反驳可以整句删去。

<a id="contrast"></a>

## 否定、反例与排比

给对比双方各写一个具体含义。只有一边有内容就直接写那一边。有真实例外、禁止事项、研究对照或容易混淆的概念时，把两边和差别写清。列举时逐项问少了它会漏掉什么，保留完整的必要项，撤去凑数的项。

<a id="proof"></a>

## 事实与归因

把每个可核实的说法指回材料。‘有人认为’有来源就写明谁在什么材料中怎么说，来源不足就去掉猜测或标待核。分清目标、观察、作者解释和已经做出的承诺。新增教学示例须让读者看出是假设，示例数据不能混成真实结果。

<a id="structure"></a>

## 长文结构

在每段旁写出读者读完获得的一个新答案。相邻段各有任务就补清关联，只有重复才合并。开头先建立读者需要的情境，收尾承担结论、下一步或叙事落点。可原封不动移到任意文章的套话通常可以删除。

<a id="plain"></a>

## 通俗解释

先写读者认识的现象或动作，再给术语和最小机制。用一个具体输入演示结果，再做一个会改变结果的变化，检查解释能否迁移。类比只用对应得上的部分，可能引出误解时加一句边界。同行入口可直接使用公认术语。

<a id="action"></a>

## 主语、动作与关系

圈出连续名词，找出哪一个是动作，以及是谁对什么做。‘开展对申请的审批工作’可以写成‘审核申请’。若原文没交代谁审核，成稿别猜。动作主体未知或不重要、研究重点在样本或过程时，被动句可以最准确。

<a id="rhythm"></a>

## 句子节奏

朗读一个完整段落，标出必须回头找主语、连接词表达错关系、句尾重复上句这三类位置。在意义边界拆句，需要读者一起比较的成分放在一起。保留自然出现的短句、复现和排比，不用句长方差或标点配额塑造声音。

<a id="locale"></a>

## 双语与地区

先确定目标读者、地区和交付物，再统一简繁、术语、数字日期、标点与空格。香港正式通知、粤语聊天、台湾技术公告各用合适语体。UI 文案和标识符保持与界面一致。双语回查义务、可能性、时态与数量，避免仅做逐字转换。

<a id="procedure"></a>

## 可执行的说明

按实际顺序写前提、动作、预期结果、失败后能采取的动作。条件只放到受它约束的步骤前。原样核对命令、参数、大小写及路径。用新用户的起点走一遍。无法验证的环境如实标出。严格受控语言项目再套用项目词表和固定句型。

<a id="engineering"></a>

## 变更与代码

按读者区分同一改动的摘要。发布说明写用户可观察的变化和迁移动作，PR 写原因与验证，注释写维护者从代码看不出的约束。确认实际 CLI/API/界面名称和支持范围，避免把设计设想写成已上线。

<a id="channel"></a>

## 渠道与工作消息

写邮件先确定收件人与请求，必要时注明负责人、日期、时区和交付方式。没有截止日期就别添。群消息留影响和下一步，公众公告补受影响对象、起止条件与办理入口，演讲稿把只能靠版式辨认的关系改成能听懂的表达。

<a id="claim"></a>

## 研究主张

在素材里找能支持中心判断的数据、例子、原始陈述或证明。把最能回答问题的证据放在主张旁，同时呈现改变解读的阴性结果或反例。已知与研究设计吻合时才用因果动词。超出材料的问题缩窄主张。

<a id="academic"></a>

## 科研体例

先确定段落的任务。方法写可复核条件，结果写比较对象及数量，讨论写解释与边界，基金申请写计划与可行性。图注写清横纵轴、组别、单位与误差含义。保持术语、公式、引语和引文归属一致。期刊、学科和作者提供的体例优先。

<a id="copy"></a>

## 产品与公众文案

把形容词换成读者能验证的功能、条件或证据。读者要操作时，按钮写动作和对象，报错写发生了什么与下一步。公告区别必须、可以和建议。商业稿里融资愿景、试点反馈和全量上线属于不同状态，分别据实交代。

<a id="genre"></a>

## 叙事、口播与体裁

先判断这句话在当前文体承担什么作用。故事里的重复可能是人物习惯，庭审或访谈逐字引语须原样，口播的停顿帮助听众保持指代。只把会妨碍该读者的模式列为编辑问题。用作者提供的场景，不给人物补经历。

<a id="verify"></a>

## 读回与交付

对照原稿和成稿查两遍。原稿中的数字、条件、否定和立场在新稿应找得到。新稿里的每个事实要能指回材料。再按读者的工作试读一次，查能否找到入口、做完操作或判断证据。事实变化优先修，等价同义词到此为止。

<a id="tools"></a>

## 工具和偏好的边界

词表、脚本、其他模型、检测分数和项目自定的标点可以提供线索。先定位句子，再举出实际的误读或信息损失才改。编辑本身可离线完成。只有用户要求相应格式或流程时才引入额外工具和交付物。

## 两条写法指向不同改法时

| 遇到的选择 | 判定问题 | 怎样落到正文 |
| --- | --- | --- |
| 建议先给结论，同时需要交代前提 | 读者能安全理解这个结论吗？ | “4 月 1 日后提交的申请需要新表格。”把生效条件和动作放在同一句，后面再放背景。 |
| 去防御性，同时需说明风险 | 删掉后会有人得出更强的判断吗？ | 删去论文里的“当然本研究难免存在诸多不足”，保留“随访只到第 30 天，第 30 天之后的复发情况未知”。 |
| 五句内说完，同时需要可执行步骤 | 少一步会使任务失败吗？ | 单句状态可压短。操作手册保留依赖顺序、验证和恢复步骤，篇幅由任务决定。 |
| 使用普通词，同时要保护术语身份 | 换词后还能在界面、日志、公式或引文中找到原物吗？ | 首次写“保留期（Retention period）”，后文依读者所见的界面复用标签。 |
| 有人要求去模板，有人要求统一格式 | 结构能帮助人比较或让程序解析吗？ | 数据字典保留相同字段顺序，客服邮件中的背景和解释则按本次问题写。 |
| 语言自然，同时符合严格机构体例 | 用户交付给哪一家机构？指定字表和可读性等级了吗？ | 有指定体例就据此审校。没有标准文本或完整审核时，具体写出做过哪些检查。 |
| 文风更鲜明，同时要忠实转述 | 谁在说、谁看到了什么？ | 作者样本可决定语气，人物经历、专家背书、用户评价和精确数值只能来自本次材料。 |
| 建议分模型校对、安装脚本或采用某种评分 | 本次任务是否真的需要这些依赖？ | 平常可用同一份原稿分别做“原 → 新”“新 → 原”两次核对。收到指定的追踪修订或词表再使用相应工具。 |

## 三个容易被误改的场景

**表单与按钮**　设原界面规定“提交后不可修改”，按钮却叫“确定”。可把按钮写成“提交申请”，并在它旁边写“提交后无法修改”。只把流程软化成“后续调整可能不太方便”，会让读者误判后果。如果草稿没说能否撤回，先查产品规定。

**研究转公众消息**　材料只说“在自愿参加问卷的 80 人中，48 人选择了 A”。研究稿可写“48/80 名答卷者（60%）选择了 A”，面向公众可写“80 名答卷者中有 48 人选择了 A”。两版都保留问卷范围，“大多数居民选择了 A”扩大了总体。

**英文工作短讯**　草稿是 “It may be worth considering the possibility of delaying the release.” 如果记录写的是负责人已经决定延期，可以改成 “We’ve postponed the release.” 如果作者只提出建议，可写 “I suggest postponing the release.” 如果记录只说明是否延期尚待决定，可写 “We haven’t decided whether to postpone the release.” 动词的选择取决于当前状态。
