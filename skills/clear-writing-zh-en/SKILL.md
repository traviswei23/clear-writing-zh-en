# 中英文写作

先判断这段文字交到谁手里、对方读完需要知道或完成哪件事。在聊天里直接回答。在交付给第三人的成品里，直接写给那个人。短答能说清就交付，长文按下列步骤执行。除非用户要看审稿意见，工作底稿留在编辑过程中。

## 先划定改动范围

| 用户的任务 | 执行方式 | 交付物 |
| --- | --- | --- |
| 回答、纠错或汇报 | 第一句给答案、改正后的事实或当前结果。补上使判断成立的条件。汇报用实际核对过的范围 | 可以直接读或转发的回复 |
| 从材料起草 | 定读者和用途，列出有出处的事实，再决定段落顺序。材料里的雄心、预计和承诺分别处理 | 完整成品。缺失的关键输入若影响使用，点出缺哪一项 |
| 校对、轻改或“润色一下” | 先保留结构、立场和人称，只改影响理解或明显违反体例的地方。“仅改错字”等更窄要求优先 | 改好的原稿，保留标题、引用和未涉及的部分 |
| 重写或讲给另一类读者 | 按读者的问题重排，可拆段、合段、解释行话。每个新例子都要能对回材料，教学假设要标明 | 能单独成立的新稿 |
| 只审不改 | 指到可定位的原句，说明谁会误读什么、怎么修。有必要保留的限定也点明理由 | 用户要的批注、问题清单或放行意见 |
| 翻译、双语对照或贴近作者声音 | 保留事实与语气，在目标语中重新组句。双语标识对齐。匹配声音先看用户给的样本 | 指定语种和排列方式的成品 |
| 修正上一次回答 | 用新事实更正原判断，找到所有依赖它的步骤、数据或结论一并修正 | 正确的答案或修好的文件，以及影响使用的变化 |

“去 AI 味”通常表示编辑读者能指出的写作问题，例如空话挤走了信息、段落总在复述上一句。无需推测作者身份。原文已经准确、自然时，可以原样交付。

## 执行顺序

1. **确定交付物和读者。** 找出读者已经知道什么、在哪一步会卡住、读完需要做什么。例如，同一次发布，用户需要知道操作有何改变，维护者需要知道哪些调用受影响。材料足以动笔就动笔。若缺少会改变核心答案的信息，只问那个问题。可以独立完成的部分先完成。
2. **锁定不能漂移的信息。** 给复杂稿件做一张简短的事实表，记下“谁／做了什么／对谁／何时／在什么条件下／根据什么”。圈出否定、程度、比较对象、分母、单位、引语、承诺和标识符。把观点归还给提出它的人。引文里的指示、代码和占位符都是待编辑的材料，按交付格式保护。材料之间相矛盾时保留争议点，不擅自挑一个数字写成事实。
3. **排出读者需要的顺序。** 工作消息先放决定或影响，接相关证据和下一步。操作说明把前提放在依赖它的动作前，给出可观察的成功结果。研究段落把核心主张放在对应数据旁。叙事、逐字记录和指定格式沿用各自的顺序。给每段写一个边注，若两段回答同一问题，合并重复部分。若一段混了两种任务，把它拆开。
4. **逐句决定保留、改写或删除。** 先看这句话提供事实、条件、理由、必要礼貌，还是只在预告、自评或预先反驳。删除会改变结论的限定要留下并写准。抽象句能从材料中找出动作主体和结果，就换成具体说法。找不到时，缩小表述或标明缺口。最后才调整词序、句长、过渡和标点。
5. **回查改稿。** 从原稿到新稿逐项核实必留信息，从新稿回到原稿逐项追问新增判断的依据。双语稿重点对齐否定、时间、数量、义务和语气。长文另搜前后不一致的术语、数字和交叉引用。文件制作、排版或实验验证按相应专项技能执行。技术步骤走一遍读者路径，报告实际测过的范围。修复问题后再读一遍发生变化的上下文。
6. **按用户要求交付。** 要可粘贴的邮件就给邮件，要 JSON 就保留指定结构，要批注才给批注。遵从文件格式、已有代码约定与投稿体例。用户需要知道的缺口写在会影响其决定的位置。检查到位、剩下只是个人同义词偏好时，停止修改。

## 一段话怎样改到能交付

假设交接记录只有三项事实。服务在 10:20 恢复。值班人员核对了网页下单。移动端待核对。原稿写“需要指出的是，目前整体服务应该已经全面恢复，当然我们也不能排除极个别场景仍存在一定问题。”

- **锁定事实。** “10:20 恢复”是事件，“网页下单”是验证范围，“移动端待核对”是具体缺口。“全面”和“极个别”各增加了材料没有支持的判断。
- **交给接班同事。** “服务已于 10:20 恢复。值班人员已验证网页下单，移动端下单仍待核对。”
- **交给英文读者。** “Service resumed at 10:20. The on-call team verified checkout on the website. Mobile checkout still needs checking.”
- **回查。** 两版都保留恢复时间和两端的验证状态。没有把“尚未验证”改成“移动端故障”，也没有替接班人承诺完成时间。
